**What I reviewed:** every Swift file in `HabitHonker/` (App, Core, Repository, Servise, Helpers, Extensions, Screens), all 18 files in `HabitHonkerTests/`, the project settings, entitlements, Info.plist, `Architecture.md` and `Docs/`.

**How:** I read the code but couldn't build it or run the tests in this session. Items marked **(verify)** depend on how the app behaves at runtime. Confirm them on a device or simulator before you fix them.

**Rule for refactors:** I only list a refactor if it fixes a bug, removes a real risk, or unblocks a step you've already planned (Architecture.md, Gamification reports). Pure naming and style changes are grouped at severity 1. Do them in isolated commits, if at all.

## Severity scale

| Sev | Meaning |
|---|---|
| **5** | Must fix. Data loss or corruption, a privacy or consent problem, or a bug users hit now. |
| **4** | Fix soon. A visible bug in a main flow, or a serious crash or performance risk. |
| **3** | Fix when you touch the area. A real bug in edge cases, a risk that will cause problems at the next planned step, or a missing safety net. |
| **2** | Worth doing. A concrete gain in UX, maintainability or future work, but not a bug today. |
| **1** | Naming, cosmetic or dead code. The logic works. |

## Severity 5

### P1: Every habit save leaves all its completion records behind as orphans (and edits can overwrite history) — **5**

**Files:** `Repository/SwiftDataRepository/HabitMapper.swift` L120–141 (`apply`) · `HabitsRepositorySwiftData.swift` L299–319 (`upsert`), L218–240 (`restoreDeletedHabit`), L197–216 (`permanentlyDeleteDeleted`) · `DeletedHabitSD.swift` L25–26 · `Core/Services/HabitService.swift` L37–51 · `Screens/AddNewHabit/HabitDetailView.swift` L53–81

**Problem**
- `HabitMapper.apply` creates brand-new `HabitRecordSD` objects for the whole history and sets `sd.records = newRecords`. Replacing a to-many relationship only clears `habit` on the old rows. `.cascade` only fires when the `HabitSD` itself is deleted, so the old rows stay in the store for good with `habit == nil`.
- `upsert` runs on every completion, priority change and edit. A habit with N records leaves N orphans on every save, so growth is quadratic: one daily habit for a year leaves about 365²/2 ≈ 66,000 dead rows. With sync on, all of them are exported to CloudKit.
- Restore (`makeSD` from the archive, then `ctx.delete(deletedSD)`) and purge also leave the archive's records behind, because `DeletedHabitSD.records` is `.nullify`.
- Orphans keep the same `id` as the live copies, so any future lookup of records by id (for example reconciling `TaskOccurrenceSD.legacyRecordID`) becomes ambiguous.
- An edit saves the `record` array that was captured when the detail screen opened (`savedItem()` copies `oldItem.record`). A completion that arrives in the meantime (for example from another device through iCloud) gets overwritten. Your Phase 3 report already lists "metadata edits can overwrite record history through HabitMapper" as a blocker before live cutover.

**Why change:** storage and sync volume grow without limit, `fetchAll` gets slower every day (it maps every record), and history can be lost. It's also a prerequisite for the gamification cutover that you've already named.

**Minimal fix**
1. Split the write API in `HabitsRepositorySwiftData`:
   - `updateMetadata(_:)` changes fields and never touches `records`.
   - `recordCompletion(habitID:at:)` fetches the `HabitSD`, finds or inserts today's single `HabitRecordSD`, and saves, all in **one** actor call.

   `HabitService.saveHabit` then calls `updateMetadata`, and `completeHabit` calls `recordCompletion`. This also fixes P4.
2. If you keep a generic `apply`, match records by `id`: update the ones that exist, insert the new ones, and `ctx.delete` the ones that were removed.
3. On restore, move the existing records over (`rec.deletedHabit = nil; rec.habit = habitSD`) instead of copying them. On purge, delete the records explicitly. Switching to `.cascade` would need a new schema version, which isn't worth doing just for this.
4. Clean up rows where `habit == nil && deletedHabit == nil` once. **Only run this when CloudKit is off, or after an import has finished.** During a CloudKit import a child row can be linked to its parent a moment later, so deleting "orphans" mid-import could delete real data.

**Test:** T1.

### P2: iCloud toggle switches between two store files, and "sync off" probably still syncs — **5 (verify)**

**Files:** `App/HabitHonkerApp.swift` L55–80 · `Helpers/SyncManager.swift` · `Screens/SettingsScreen/SettingsView.swift` L29–58

**Problem**
- With sync on, the app uses `ModelConfiguration("Cloud", …)`, which is `Cloud.store`. With sync off, it uses `ModelContainer(for:migrationPlan:)` with the default configuration, which is `default.store`. These are **different files**. Turning sync on shows a different dataset (empty until the CloudKit import finishes). Turning it off brings back the old local data and hides everything created while sync was on. Your `GamificationMigrationTests` even prints both URLs.
- The "off" path uses the default `ModelConfiguration`, whose `cloudKitDatabase` is `.automatic`. Because the app has the iCloud/CloudKit entitlement, `.automatic` uses that container. So the "local" store is very likely mirrored to the same private database **even after the user turned sync off**. That's a consent and privacy problem, and both files then mirror into the same zone.
- The live teardown (`container = nil; await Task.yield()`) doesn't guarantee the old store has been released, because the repository actor and any in-flight Tasks still hold it. If reopening fails, you land in P3's in-memory fallback. Toggling also rebuilds the whole UI, which sends the user back to the List tab.

**Why change:** users see "my data disappeared", and their data leaves the device against a setting they chose.

**Verify first:** launch with `-com.apple.CoreData.CloudKitDebug 1`, sync off, signed into iCloud, and look for export activity in the console. You can also check the CloudKit Console for records created while sync was off.

**Fix**
- Local mode: pass `cloudKitDatabase: .none` explicitly and keep the default store URL. Your test already asserts the URL stays stable.
- Prefer **one store file** for both modes and switch only the CloudKit option. Apply the change on next launch (with an explicit "restart to apply" step) instead of tearing the store down live. If you keep two files, copy or merge on enable, and tell the user what happens on disable.
- Existing users already have data in `Cloud.store`. Decide their one-time migration before you change any store URL.

### P3: If the container can't be created, the app silently runs on an in-memory store — **5**

**Files:** `App/HabitHonkerApp.swift` L69–95

**Problem:** every `ModelContainer` creation uses `try?`. On failure the app builds `FallbackInMemory` and carries on as normal. Everything the user adds in that session is gone when the app quits, with no message and no logged error. Possible triggers: a migration failure (see P6), CloudKit schema validation, a full disk, or the teardown race in P2. A failed **cloud** container also falls back to memory instead of to the local store.

**Why change:** this turns any persistence failure into silent data loss. Architecture.md and ManualQA already mark it "fragile", and the fix is cheap.

**Fix:** move container creation into a small `PersistenceController` type. Today this logic lives inside the `App` struct and has no tests; as a plain type it becomes testable (T2). Try in this order: the requested mode, then the local on-disk store, then a **blocking error screen** that explains the problem. Never hand the user a writable store that will be thrown away. Log the underlying error.

## Severity 4

### L1: One-time tasks become "not completed" again the next day — **4**

**Files:** `Screens/TaskList/HabitModel.swift` L46–48 · `Core/Services/HabitSortFilterService.swift` L9–19, L52–78 · `Screens/TaskList/HabitListView.swift` L177–187 · `HabitCell.swift` L17

**Problem:** "completed" always means "has a record on `currentDate`". That breaks `.dueDate` tasks. Say you complete one today. Tomorrow it moves back to "Not for today" as incomplete and can be swiped again. On its due date it shows up in today's list as not done. Sorting (`isCompletedToday`) has the same problem.

**Why change:** the core list logic is wrong for a whole task type, every day.

**Fix:** use one rule, `isDone(asOf:)`: a repeating habit is done if it has a record on that day; a due-date task is done if it has any record at all. Use it in the three filters, in `sorted`, and in `HabitCell`. **Test:** T3.

### L2: Errors are stored but never shown — **4**

**Files:** `HabitListViewModel.swift` L19 · `PriorityMatrixViewModel.swift` L21 · `SettingsViewModel.swift` L21 · `StatisticsViewModel.swift` L18 · `SelectHabitsViewModel.swift` L26 · `HabitDetailView.swift` L300–303

**Problem:** every ViewModel has an `error`, but no view reads it. The only two alerts in the app are the delete confirmation and the iCloud hint. Failures to save, delete, complete, change priority or set the background are all invisible. `HabitDetailView` fires the save in a `Task` and closes immediately, so a failed save looks like a success. Your `NotificationInvestigationTests` check that `vm.error` gets set; the UI just never reads it.

**Fix:** add one `.alert` per screen bound to the ViewModel's `error`, and clear it on dismiss. For the detail screen, make save async (`saveAction: (HabitModel) async -> Bool`) and dismiss only after it succeeds.

### U1: Background image is rendered at 3× size and decoded again on every render — **4**

**Files:** `Helpers/BackgroundStorage.swift` L32–46 · `Screens/TaskList/HabitListViewModel.swift` L37–46 · `HabitListView.swift` L156–172 · `SettingsViewModel.swift` L114

**Problem**
- `UIGraphicsImageRenderer(size:)` uses the screen scale, which is 3× on iPhone. "Downscale to 3000" actually renders about **9000×6750 px** for a normal photo, which is bigger than a 12 MP original. For a 48 MP photo the pipeline needs about 190 MB to decode and about 240 MB to render, so the app can be killed for memory use.
- `backgroundUIImage` is a **computed property** that decodes the JPEG and redraws it into a new bitmap every time it's read, and `HabitListView` reads it in `body`. Every list update (completion, load, event) re-decodes a ~240 MB bitmap on the main thread. The code comment says "pre-decode once", but a computed property runs every time.
- `UIGraphicsBeginImageContextWithOptions(…, opaque: true, …)` is deprecated and drops alpha.

**Fix:** set `format.scale = 1` and target the screen's pixel size (about 2800 px on the long side). Better still, create the thumbnail with ImageIO (`CGImageSourceCreateThumbnailAtIndex`) so the full image is never decoded. In the ViewModel, decode once when the data changes (`preparingForDisplay()`, off the main thread) and publish a stored `UIImage?`. **Test:** T8.

## Severity 3

### S1: Habit titles are written to system logs as public — **3**

**Files:** `Helpers/Logger.swift` L38–51 · `HabitsRepositorySwiftData.swift` L100, L115 · `HabitListViewModel.swift` L128, L219 · `HabitModel.swift` L25–44 · `PriorityMatrixView.swift` L130

**Problem:** habit titles are logged with `privacy: .public`, and your `Logger` extension overloads force `.public` onto *every* String message. Unified logs can be read through Console and sysdiagnose, and habit titles can be sensitive (health, medication, private goals). The `print`s in `completeHabitNow` run in release builds too.

The attack surface is otherwise small: no network, no web views, no URL schemes, no secrets in the repo. Logs, iCloud consent (P2) and data retention (S2) are the real privacy issues.

**Fix:** log IDs only, or use `privacy: .private` / `.private(mask: .hash)` for titles. Delete the String overloads, which make leaks easy, and the `print`s. `Log.isEnabled` can become `#if DEBUG`.

### S2: "Deleted" habits are never deleted, but the UI says they are — **3**

**Files:** `HabitDetailView.swift` L351–359, L395 · `HabitsRepositorySwiftData.swift` L136–161 · `HabitListViewModel.swift` L214–240

**Problem:** deleting a habit archives its title, description, tags and full history into `DeletedHabitSD`, which also syncs to iCloud. There is no UI to restore or purge it: restore and permanent delete are only reachable from tests. Yet the confirmation says *"This action cannot be undone."* The only place archived habits show up is Statistics → Select habits → "Deleted habits". Restore also doesn't reschedule reminders.

**Why change:** telling users their data is deleted when it's kept is a privacy and trust problem, and archived habits pile up forever.

**Fix (a product decision):**
- **(a)** Keep soft delete. Change the message (e.g. "Moved to archive. It stays in your statistics.") and add an Archive screen with *Restore* and *Delete permanently*. Reschedule reminders on restore.
- **(b)** Delete for real and remove the archive path. You lose statistics history for deleted habits, so decide that deliberately.

### P4: Read-modify-write of the whole habit isn't atomic across screens — **3**

**Files:** `Core/Services/HabitService.swift` L37–51 · `Core/Services/HabitMutationCoordinator.swift` · `HabitListViewModel.swift` L25 · `PriorityMatrixViewModel.swift` L75–89

**Problem:** `completeHabit` and `changePriority` fetch, change and upsert in two separate actor calls, and they write the **entire** model. `HabitMutationCoordinator` only orders operations inside `HabitListViewModel`; `PriorityMatrixViewModel` doesn't go through it. So a priority drag and a completion on the same habit can interleave, and the later upsert writes a stale copy (losing either the completion or the priority). The window is small today, but it grows as fetches get slower (P1).

**Fix:** you get this for free with P1's API split: do each change inside one actor method (`recordCompletion`, `setPriority(id:)`). Keep the coordinator for ordering notification side effects; it just stops being the only thing protecting the data. **Test:** T5.

### P5: Changes from iCloud never refresh the UI or reminders — **3**

**Files:** `App/HabitHonkerApp.swift` · `Core/Services/HabitEventCenter.swift` · `HabitListViewModel.swift` L169–176 (and the same subscription in the matrix and statistics ViewModels)

**Problem:** screens only reload on local `HabitEvent`s. Imports from another device don't send one, so the list, matrix and statistics stay stale until the user does something or relaunches. Reminders are per device: a habit created or edited on device B never gets its notifications scheduled on device A.

**Fix:** observe `NSPersistentStoreRemoteChange` (or context-save notifications for the container) and forward it as a coarse `.remoteChange` `HabitEvent`. On that event, reschedule reminders. Doing it for all habits is cheap, because iOS caps you at 64 pending notifications anyway.

### P6: Schema V1 and V2 use the live model classes — **3**

**Files:** `Repository/SwiftDataRepository/HabitSchemaMigration.swift` L3–18

**Problem:** `HabitHonkerSchemaV1.models` points at the *current* `HabitSD`, `HabitRecordSD`, etc. The comment says to keep them frozen, but only the attribute-inventory test enforces that. The first time a field is added to `HabitSD`, V1 no longer matches what's stored on users' devices, so migration fails, the app falls into P3's fallback, and data is silently lost.

**Fix:** before the **next** model change, copy V1 and V2 into nested frozen types (`enum HabitHonkerSchemaV1 { @Model final class HabitSD { … } }`) and make the app's type names point at the latest version. You don't need to do this now, but do it in the same PR as that model change, never after it. **Test:** T6.

### P7: The gamification transaction treats duplicates as fatal — **3 (latent)**

**Files:** `Repository/SwiftDataRepository/BehaviorTransactionSD.swift` L13–46 · `GamificationSD.swift`

**Problem:** the transaction throws when it finds two rows for the same profile key, occurrence, ledger key or command. CloudKit can't enforce uniqueness. If two devices each create a profile, or complete the same occurrence offline, they'll sync into duplicates, and from then on **every** completion throws `duplicateProfileKey` / `duplicateOccurrenceKey`. Your Phase 3 report already says "Cloud duplicate reconciliation is not implemented".

**Why now:** it isn't live, so users aren't affected yet. But it decides whether the cutover works for anyone with two devices. Design a deterministic merge (for example: keep the lowest UUID, merge by logical key) **before** wiring it in. Otherwise the calculators and the transaction look solid and are well tested; don't change them.

### L3: `isLoading` guards drop reload requests — **3**

**Files:** `HabitListViewModel.swift` L93–97 · `PriorityMatrixViewModel.swift` L44–46 · `StatisticsViewModel.swift` L48–50 · `SettingsViewModel.swift` L41 · `SelectHabitsViewModel.swift` L46

**Problem:** if an event arrives while a load is running, the new load returns immediately and its data is never shown (for example, a priority change from the matrix while the list is loading). Every event also triggers three full reloads of all habits and records (list, matrix, statistics).

**Fix:** replace "skip if loading" with "load again when the current load finishes" (a `needsReload` flag), or cancel and restart the load task. Debouncing events by 100–200 ms is optional. **Test:** T7.

### L4: Alarm changes run before the save; failures are hidden — **3**

**Files:** `HabitListViewModel.swift` L125–141, L248–258 · `Servise/HabitNotificationService.swift` L23–31

**Problem:** your `testReproduces…` tests already describe this:
- Save schedules the alarm *before* the upsert, so a failed save leaves an orphan alarm.
- Delete cancels the alarm *before* deleting, so a failed delete leaves a habit with no alarm.
- `try? reschedule` hides scheduling errors.
- Denied notification permission is never checked, so the cell shows "Remind me at" but nothing fires.

**Fix:** save first, then schedule or cancel. If scheduling fails or authorization is `.denied`, show it (using the alerts from L2) and mark the reminder row as "Notifications are off in Settings". Your "Reproduces" tests then become regression tests.

### L5: iOS keeps only 64 pending notifications — **3**

**Files:** `Servise/HabitNotificationService.swift` L80–100

**Problem:** repeating habits schedule one request per weekday, so up to 7 per habit. Around 10 daily habits with reminders is enough for iOS to silently drop everything past 64.

**Fix:** for habits that repeat every day, schedule **one** daily trigger (hour and minute only) instead of seven. Count the total and warn the user as it approaches 64 (or keep the highest-priority ones).

### L6: No validation on the habit form — **3**

**Files:** `Screens/AddNewHabit/HabitDetailView.swift` L253–303

**Problem:** you can save:
- an empty title;
- a repeating habit with no weekdays, which never appears in today's list and whose reminder schedules nothing (see `testRealSchedulerPersistsEnabledEmptyWeekdaysWithNoRequests`);
- a due-date task in the past with a reminder on, which is silently skipped.

**Fix:** disable Save when the title is blank, or when `type == .repeating && repeating.isEmpty`. Show a hint when the due date is in the past and the reminder is on.

### L7: A completion can't be undone — **3**

**Files:** `HabitListView.swift` L75–94 · `HabitModel.swift` L25–44

**Problem:** rows in the Completed section have no action. An accidental swipe permanently adds a record and a statistics pill, and a double swipe increases the count.

**Fix:** add an "Undo today" swipe action on Completed rows. Implement it as a repository method next to P1's `recordCompletion`.

### U2: Tapping the trash icon to clear the background mostly opens the photo picker — **3**

**Files:** `Screens/SettingsScreen/SettingsView.swift` L85–124

**Problem:** the clear control sits *inside* the `PhotosPicker` label, and `onTapGesture` is attached to the rounded rectangle *under* the trash image. A tap on the icon itself falls through to the picker. Only the edge clears the background, and VoiceOver can't reach it.

**Fix:** move "Remove background" out of the picker label into its own `Button(role: .destructive)` row, shown only when a background is set.

### U3: Priority matrix clips habits when a quadrant is full — **3**

**Files:** `Screens/PriorityMatrix/PriorityMatrixView.swift` L110–146

**Problem:** each quadrant is a fixed-height, clipped `VStack`. With more than about 4–6 habits in a quadrant (fewer on small phones or with large text), the rest are cut off: invisible and impossible to drag. Tapping a chip only runs a `print` (a TODO).

**Fix:** put the quadrant content in a `ScrollView`, or use a flow layout with "+N more". Then either connect the tap to the detail screen or remove the tap handler.

### U4: Accessibility gaps in core actions — **3**

**Files:** `Helpers/CustomSwipeAction.swift` · `HabitListView.swift` L37–44 · `HabitCell.swift` · `WeekdayPicker.swift` L37–41 · `PriorityMatrixEditorView.swift` L94–107 · `HabitFilterCollection.swift` L44–47

**Problem**
- Completing a habit is only possible with the custom pan gesture. VoiceOver and Switch Control users can't do the app's main action.
- Rows use `onTapGesture`, so they have no button trait.
- The theme editor's Save is a tapped `Circle`, not a `Button`.
- Filter chips put white text on the user's chosen color at 50% opacity, which can have poor contrast.
- Fixed heights (the 31 pt reminder row, 74 pt day cells) cut off text at large Dynamic Type sizes.

**Fix (no rewrite of the swipe component):**
- Add `.accessibilityAction(named: "Complete")` to the cell.
- Use `Button`, or `.accessibilityAddTraits(.isButton)`, for tappable rows.
- Make the editor's Save a `Button`.
- Pick black or white chip text based on how light the color is.

### U5: `DateFormatter` churn and hard-coded date formats — **3**

**Files:** `Screens/StaisticsScreen/DayCell.swift` L44–56 · `Extensions/WeekdaySet.swift` L23–26 · `Extensions/Date + Extension.swift` L10–26 · `CalendarBuilder.swift` L61–64

**Problem**
- A new `DateFormatter()` is created inside view bodies. `DayCell` creates **two per cell per render** (about 730 for a full year), and `Weekday.shortSymbol` creates one per weekday cell. This is the main cost of scrolling Statistics.
- `getTimeFrom()` forces "h:mm a", which ignores the user's 24-hour setting.
- `currentDayTitle` builds "Wednesday 23, September" by hand instead of using the locale's format.

**Fix:** use cached static formatters or `Date.FormatStyle`, e.g. `date.formatted(date: .omitted, time: .shortened)` and `.dateTime.weekday(.wide).month(.wide).day()`.

## Severity 2

### L8: Detail route falls back to a mock habit with a new ID — **2**

**Files:** `HabitListView.swift` L123–124

If the habit isn't in `viewModel.items` (for example, it was deleted through sync while you were navigating), the editor opens `HabitModel.mock()` with a random UUID and a random color, and Save creates a ghost habit. **Fix:** show "This habit no longer exists" and go back.

### L9: Day change is only detected by a 60 s timer — **2**

**Files:** `HabitListView.swift` L97–105, L190–209

The timer only runs while the list is on screen. If you return to the app after midnight, you see yesterday's lists for up to a minute (longer if you open another tab first). **Fix:** react to `scenePhase == .active` and `UIApplication.significantTimeChangeNotification`, which also covers time zone changes.

### L10: Statistics can only show the current year — **2**

**Files:** `StaisticsView.swift` L12, L70, L115–118 · `CalendarBuilder.swift` L70–87

Nothing in the UI changes `selectedYear`, so in January you see a single month and last year's history can't be reached. `regenerateYear` is never called. **Fix:** add year paging (previous/next), or show a rolling 12 months.

### L11: Saving the statistics selection races with dismiss — **2**

**Files:** `SelectHabitsView.swift` L64–69

The code runs `Task { await persistPreset() }` and then `dismiss()`, so the parent's `onAppear` reload can read the old selection. No event is sent after saving. **Fix:** `await` the save and then dismiss, or send an event after saving.

### A8: API hygiene and misc

- **Injected objects:** `@StateObject` wraps objects passed in from outside (`PriorityMatrixView` L24/30, `SettingsView` L16/21, `StaisticsView` L15/23). Use `@ObservedObject`. It works today only because the parent never recreates them.
- **Deprecated APIs:** `foregroundColor`, `.navigationBarTrailing`, `edgesIgnoringSafeArea`, `presentationMode` (`HabitDetailView` L50, unused), `.cornerRadius`, `UIGraphicsBeginImageContextWithOptions`, `TextField(onCommit:)`.
- **Icon distortion:** `HabitCell`'s icon modifiers are in the order `resizable → frame → scaledToFit` (L30–34), which stretches non-square icons. Use `resizable().scaledToFit().frame(…)`.
- **Unused imports:** `AuthenticationServices` (SettingsView), `CloudKit` (HabitHonkerApp), and `SwiftData` in views that don't use it.
- **Drag payload type:** `HabitDragPayload` uses the generic `.data` type (`PriorityMatrixView` L14–19), so on iPad any dropped data is offered to the matrix. Declare a custom UTType.
- **Swipe scroll check:** `CustomSwipeAction` stores the *horizontal* offset in `storedScrollOffset` and compares it with the *vertical* scroll position (L57–58, L94–100, L140–143), and `currentScrollOffset` is unused. It works by accident, since any scroll resets the swipe. Leave it unless you're already editing the file.
- **Redundant hops:** `await MainActor.run` inside `@MainActor` classes (`SyncManager` L19/21, `StatisticsViewModel` L56) does nothing.
- **Background storage:** `BackgroundStorage` writes with `try?`, so failures are invisible, and it writes into Documents. Application Support is the better place for app-internal files.
- **`.continue/config.json`:** this is local AI-tool config. Add it to `.gitignore` if it's tracked.

- **Replacing `HabitModel` with `BehaviorTarget` in production now.** Your step-by-step plan (shadow mapper, flags) is the right order; switch at cutover.
